# 成本模型与估算（面试话术）

> 用途：回答"你这个系统跑一次问答花多少钱？"。
> ⚠️ 表格中的单价为**示例价格**，投简历/面试前请用你实际账单或最新官方价替换
> （Langfuse 每个 trace 都有 token 用量，直接统计最准）。

## 一次 RAG 问答的 token 构成

```
输入 token =
    系统/工具描述 prompt
  + 检索上下文（top_k=4 × 块长 800 字符 ≈ 2-4K token；rerank 输入另算）
  + 多轮历史（可选，本项目默认只带最近 2 轮）
  + 用户问题
输出 token = 最终答案（通常 0.3-0.8K token）

若走子 Agent（rag_agent）：检索上下文会再进一次子 Agent 的 LLM 调用，
supervisor 拿到结果后总结 → 实际约 1.5~2 次 LLM 生成。
```

## 示例估算（单价需替换）

| 项 | 假设 | 单价（示例） | 成本 |
|---|---|---:|---:|
| 输入 token | ~3.5K（含检索块） | ¥0.002/K | ¥0.007 |
| 输出 token | ~0.6K | ¥0.008/K | ¥0.005 |
| rerank | 6 候选 × 单次推理 | ~¥0.0005 | ~¥0.0005 |
| **单次问答合计** | | | **≈ ¥0.012~0.015** |
| 1,000 次问答 | | | ≈ ¥12~15 |

> 话术："单次问答约 1-2 分钱，主要成本在输入侧的检索块 token；1000 次对话十几块钱。
> 这个量级下，'省几块钱 token' 远不如'把检索质量做对'重要——所以我先解决准确率，再优化成本。"

## 成本优化手段（对应项目真实配置）

1. **块预算** `rag_max_total_chars`：限制喂给 LLM 的检索文本总量（预算即成本上限）。
2. **rerank 候选限流** `rerank_candidate_k=6`：精排只算 6 条，控制 CPU/API 推理量。
3. **查询改写默认关**：评估显示改写检索侧无增益，省掉额外 LLM 调用。
4. **轻量子 Agent 模型** `llm_light_model`：rag/mcp 子 Agent 用小模型，supervisor 用主模型。
5. **嵌入缓存** `embed_query_cached`：相同 query 不重复推理。
6. **记忆裁剪**：多轮上下文只带最近 2 轮，控制历史 token 增长。

## 评估成本（一轮实验）

```
40 条 GT × 4 指标 × judge 调用（输入约 0.8-2K、输出 ~0.1K，temperature=0）
≈ 160 次 judge 调用 ≈ 每次 ~¥0.003 → 一轮评估 ≈ ¥0.5 左右
```

> 话术："评估闭环本身很便宜——一轮四指标评估不到一块钱，但能避免一次错误的参数上线。
> 这也是我敢把所有实验开关都做成可 A/B 的原因。"

## 实测方法

- Langfuse trace：每次对话/子任务都有 token 用量与耗时，按天聚合即真实成本。
- 压测脚本 `benchmark.py --endpoint chat`：可同时拿延迟与调用次数。
