## 1. 子系统总览

```
┌──────────────────────────────────────────────────────────────────────┐
│                          写入链路（ingest）                            │
│  上传文件 → 原始文件持久化(uploads/<uuid>/) → 后台线程摄入               │
│    → 解析(编码检测/HTML/PDF/DOCX) → 分块(Markdown标题+递归)             │
│    → sha256 指纹增量对比 → 仅嵌入新增块 → 写 Milvus + Postgres          │
└──────────────────────────────────┬───────────────────────────────────┘
                                   │ 失效签名缓存
┌──────────────────────────────────▼───────────────────────────────────┐
│                           查询链路（retrieve）                         │
│  search_knowledge_base 工具(按 user_id 隔离)                            │
│    → retriever.invoke(query)                                          │
│        ├─ 通道1: Milvus 向量检索（IP 相似度 + user 过滤）                 │
│        ├─ 通道2: Postgres 文本 BM25（jieba/单字分词）                   │
│        └─ RRF 融合 → CrossEncoder rerank 精排                          │
│    → 同文档去重 + 相邻块合并 + 超长块截断（上下文压缩）                     │
│    → LangChain Document[] → RAG Agent 生成 → 引用溯源(sources)          │
└──────────────────────────────────────────────────────────────────────┘
```

- **存储双写**：`Milvus` 存向量（`id` 与 Postgres `documents.id` 一一对应），`Postgres` 存文本与元数据（同时是 BM25 通道的数据源）。
- **设计哲学**：向量索引本质是**文本的"缓存"**（派生视图），因此项目围绕"缓存失效"做了大量工作——见 [4](#4-增量摄入--内容指纹去重) 与 [13](#13-rag-常见失败模式--本项目的应对)。

## 2. 数据摄入与文件解析

### 2.1 支持格式与解析策略

| 格式 | 解析实现 | 关键设计 |
|------|---------|---------|
| txt/md | `_read_text_auto` | **chardet 自动检测编码**，检测失败回退 `utf-8` 容错（`errors="ignore"`） |
| html/htm | `_HtmlTextExtractor` | stdlib `html.parser` 提取可见文本，**显式丢弃 `<script>/<style>`** |
| pdf | `pypdf.PdfReader` | 逐页 `extract_text()`，空页容错 |
| docx | `_docx_to_text` | **段落 + 表格双通道**，表格单元格用 `\|` 拼接 |

### 2.2 为什么这样设计

- **chardet 自动编码检测**：中文文档大量使用 GBK/GB2312 编码，固定 `utf-8` 会乱码、丢字。检测是"尽力而为"（`except Exception: pass`），失败仍能兜底，属于**渐进增强**而非硬依赖。
- **HTML 丢弃 script/style**：这类标签内的内容对问答无价值（脚本、样式文本），混入知识库会成为**噪声**，稀释 embedding 语义、拉低检索精度。用 `_skip_depth` 计数器处理嵌套。
- **DOCX 表格纳入**：如果只取 `doc.paragraphs`，大量以表格呈现的信息（参数表、对照表、价格表）会**永久丢失**——这类恰恰是高价值精确信息（用户检索"表里的数据"）。

### 2.3 潜在问题与解法

| 问题 | 解法 |
|------|------|
| PDF 是**扫描件**（图片型）时 `extract_text()` 返回空 | 接入 OCR（PaddleOCR / Tesseract）作为解析后端；或至少在返回"无内容"时**显式提示用户**，避免静默丢内容 |
| DOCX 表格单元格拼接后失去行列结构 | 拼接时保留表头，或在 metadata 中记录"该块来自表格"，必要时走高精度表格解析（Table Transformer 类模型） |
| 大文件解析耗时 | 本已放后台线程（见 [12](#12-api-设计与后台任务)），可再加并发限制（信号量）避免多个大文件同时打爆 CPU |
| HTML 只取文本丢失链接/引用 | 可保留链接文本做溯源；当前场景以内容问答为主，可接受 |

## 3. 分块策略

### 3.1 实现要点（`ingestion.py::split_text`）

```
Markdown（以 # 开头）
  → MarkdownHeaderTextSplitter 按 H1/H2/H3 切"章节"（strip_headers=False 保留标题）
  → 每章节内 RecursiveCharacterTextSplitter 再递归分块
  → metadata 携带 Header1/Header2/Header3 章节层级

非 Markdown
  → RecursiveCharacterTextSplitter 直接递归分块
    chunk_size=800, chunk_overlap=100
    separators = ["\n\n", "\n", "。", "！", "？", ". ", "! ", "? ", " ", ""]
```

### 3.2 为什么这样设计

- **"分块决定 RAG 质量 70%"**（业界共识）。分块过小：语义丧失殆尽；过大：噪声淹没相关片段。本项目用**递归 + 结构化**组合而非纯定长：
  1. **Markdown 按标题切分**：纯长度切分切断"标题 ↔ 正文"联系。按标题分块让每块自带语义边界与章节上下文，检索命中块时能携带**所在章节标题**，中文文档召回质量提升显著。
  2. **中文友好的分隔符优先级**：`段落 → 换行 → 句号/叹号/问号 → 空格`,保证分块**在完整语义单元处断裂**,而非生硬按字符截断。
  3. **chunk_overlap=100（约 12%）**：业界推荐重叠 10%~20%。防止跨块边界的关键信息丢失（如一段论证横跨两个块时，检索只命中后一半）。
- **保留标题（strip_headers=False）**：让"章节标题文本"作为前缀出现在块文本中，提升 embedding 的语义锚定性。

### 3.3 为什么不用更高级的分块

| 方案 | 为何本项目不采用 |
|------|-----------------|
| 纯语义分块（`SemanticChunker`/embedding 断点） | 计算开销大、块长不一；本项目 Markdown 文档天然有标题结构，结构化切分已优于语义断点，且**无额外推理成本** |
| 滑动窗口 | 块数量膨胀（存储/检索成本↑），仅法律/金融等强跨句语义场景才值得 |
| LLM 分块 | 最准但最贵、最慢，不适合批量摄入 |
| 固定大小 | 已有，但作为递归的**兜底层**而非主策略 |

### 3.4 潜在问题与解法

| 问题 | 解法 |
|------|------|
| 非 Markdown（纯文本/PDF/DOCX）没有标题结构 | 可引入"伪标题"启发式（如识别 `第X章`、全大写行、目录项），或对 PDF 做版面分析（layout）后结构化；当前按段落切分已够用 |
| 表格被文字切碎 | docx 已按行拼接；PDF 表格需专用解析（见 2.3） |
| 同一文档重复上传，分块边界变化导致"看似变化" | 已由指纹去重缓解——内容未变的块 sha256 相同则跳过（见 [4](#4-增量摄入--内容指纹去重)） |
| chunk_size 一刀切不适合所有文档类型 | 可按文档类型/标签细分块参数（如代码块用小块、综述用大块），`RAG_MAX_CHUNK_CHARS` 已在检索侧兜底截断 |

## 4. 增量摄入 / 内容指纹去重

### 4.1 实现要点（`ingestion.py::ingest_file`）

```
source = str(path.resolve())          # 文档唯一标识 = 绝对路径
chunk_hash = sha256(text).hexdigest() # 块指纹

1) 解析 + 分块成功后才动数据（原子性）
2) 读该用户已有同 source 的块: hash -> id 映射
3) 对比:
   - 内容相同的块      → 跳过（不重复嵌入/写入）
   - 新增/变化块       → 嵌入 + 写入（chunk_index 用原始索引）
   - 旧文档消失的块    → 从 Postgres + Milvus 双删
4) 全部未变化          → 返回 unchanged=True，零写入、零删除
5) commit 后 invalidate_docs_signature()（使 BM25 索引重建）
```

### 4.2 为什么这样设计（对应业界"检索级联失效"问题）

《检索级联失效》指出：**文档已从事实源消失，但 embedding 仍留在索引中**，不断为模型提供"幽灵"。根因往往是稳定的文档 ID/分块 ID + **sidecar 映射表**缺失，导致删除时无法可靠列出"属于某文档的所有分块"。

本项目正是围绕这一层防御设计的：

- **稳定 ID**：`source` = 绝对路径，块 `id` 写入时生成并持久化到 Postgres —— **Postgres 就是 sidecar 映射表**（`Document.user_id/source/chunk_index` → `id`），唯一约束 `(user_id, source, chunk_index)` 保证幂等。
- **先对比后写入**：避免"删旧增新"在更新场景下把未变化的块也重嵌入（**省 embedding 成本 + 缩短摄入延迟**）。
- **双写双删**：Postgres 删除 + `vector_store.delete_by_ids(stale_ids)` 精确按主键删向量 —— 两库保持一致，杜绝索引残留。
- **原子性**：先解析成功再删旧增新；失败时旧数据不受影响。
- **整篇无变化零写入**：重复上传相同文件零成本（也是对用户重复上传的友好处理）。

### 4.3 潜在问题与解法

| 问题 | 解法 |
|------|------|
| **读后写竞争**（用户问题检索到的块，在生成期间源文档被修改/删除） | 见 [13](#13-rag-常见失败模式--本项目的应对)：分块加版本号/检索时校验/引用前重验证 |
| `path.resolve()` 作 source，容器/Pod 挂载路径改变则全部失效 | 可用内容 hash + 相对路径联合标识；当前为本地部署可接受 |
| 增量对比需读取该 source 全部块的 text（内存） | 单文档块数通常数百内，可控；超大文档可改为指纹表预查询 |
| 摄入中途失败（embedding 服务抖动） | 先解析 → 再删旧 → 后增新的顺序，保证失败时旧数据未被破坏，重试即可收敛 |

## 5. Embedding

### 5.1 实现要点（`embedding.py`）

| Provider | 实现 | 关键细节 |
|----------|------|---------|
| `local`（默认） | sentence-transformers `BAAI/bge-small-zh-v1.5`（512 维） | `normalize_embeddings=True`；`local_files_only=True` 离线加载 |
| `openai` | `OpenAIEmbeddings` | 兼容任意 OpenAI 格式 endpoint（text-embedding-3-small 等） |

`@lru_cache` 全局单例。

### 5.2 为什么这样设计

- **默认中文友好模型**：`bge-small-zh-v1.5` 对中文检索效果优于通用多语模型，且 **512 维**（比 1024/1536 更省 Milvus 存储、CPU 推理更快）。
- **normalize ⇒ IP 度量**：归一化后内积（IP）≈ 余弦相似度，因此 Milvus 用 `metric_type="IP"`，省去余弦的额外开销（见 [6](#6-向量存储milvus)）。
- **双 provider 解耦**：不绑定单一云端——生产用 OpenAI 兼容 embedding，本地/离线用本地模型，**同一检索代码无感切换**。
- **离线加载**：`local_files_only=True` 避免 HF 网络不可达时联网 HEAD 检查卡住（项目 `HF_OFFLINE` 配置的落地动作）。

### 5.3 潜在问题与解法

| 问题 | 解法 |
|------|------|
| 嵌入模型与业务领域不匹配（法律/医学术语） | 在 MTEB/BEIR 榜单 + 自己的测试集上选型（见 [15](#15-评估方法论)），必要时领域微调 |
| 维度变更需要重建集合、全量重嵌 | `vector_store._validate_embedding_dim` 做了**维度校验防静默错配**；确有需要时写全量重索引脚本 |
| 查询短、文档长 → 语义鸿沟 | 见 [8](#8-混合检索与-rrf-融合)（加 BM25 通道）与 [13](#13-rag-常见失败模式--本项目的应对)（Query 改写/HyDE） |
| 批量嵌入耗时 | 摄入是后台线程天然非阻塞；前端轮询展示进度（见 [12](#12-api-设计与后台任务)） |

## 6. 向量存储（Milvus）

### 6.1 Schema 设计（`vector_store.py::_build_schema`）

| 字段 | 类型 | 设计意图 |
|------|------|---------|
| `id` | VARCHAR(32) 主键 | 块唯一 id（uuid4.hex） |
| `doc_id` | VARCHAR(32) | **对应 Postgres `documents.id`**——两库一致，是"sidecar 映射"的关键 |
| `user_id` | VARCHAR(64) | **按用户隔离**的过滤字段 |
| `source` | VARCHAR(500) | 文档绝对路径，加速按文档删除/过滤 |
| `chunk_index` | INT64 | 块序号（配合 doc_id 构成融合键） |
| `text` | VARCHAR(8000) | 块文本（检索时不取，便于排障） |
| `metadata_json` | VARCHAR(2000) | 章节标题等附加元数据 |
| `embedding` | FLOAT_VECTOR(dim=512) | 向量 |

`enable_dynamic_field=False`：**拒绝动态字段**，强制 schema 一致，避免脏数据写入。

### 6.2 索引设计（`_ensure_indexes`，幂等创建）

| 索引 | 类型 | 用途 |
|------|------|------|
| `embedding` | IVF_FLAT + IP，nlist=128 | 相似度检索 |
| `source` | Trie（标量） | 加速按文档删除/过滤 |
| `user_id` | Trie（标量） | 加速按用户隔离的过滤 |

### 6.3 为什么这样设计

- **标量索引（source/user_id）是生产级检索的隐性关键**：向量库只建向量索引、不建标量索引，`filter` 就退化为全表扫描，数据量大时检索/删除显著变慢。这里与向量索引**一起幂等创建**。
- **IVF_FLAT + nlist=128**：中小规模数据（数万~百万块）IVF_FLAT 精度高、构建简单；`nprobe=16` 是召回/延迟的常见平衡点。规模更大时可换 HNSW/IVF_PQ。
- **先取 `top_k*3` 再按阈值过滤**：IP 阈值过滤后实际命中可能不足 `top_k`，先放大召回再过滤，避免"漏返回"。
- **`_validate_embedding_dim` 维度校验**：换 embedding 模型后维度不匹配会在写入时静默失败/错乱，本项目启动时校验并降级。
- **度量选择（IP vs COSINE 实证）**：embedding 已归一化（`normalize_embeddings=True`），归一化后内积==余弦，二者检索结果逐条一致（实测 MRR 0.944 / Hit@1 0.900 完全相同）；默认 `IP`（最快）；`MILVUS_METRIC_TYPE=COSINE` 可切——COSINE 内部归一化 query，对「未来漏归一化的模型」更防御，且分数恒在 [-1,1] 更可解释。**切换需重建索引**（metric 是索引参数，不能热改）。

### 6.4 潜在问题与解法

| 问题 | 解法 |
|------|------|
| Milvus 删除存在**墓碑/延迟清理窗口**（HNSW 类索引通用行为） | 本项目是"按主键显式删除" + Postgres 权威源；需更强一致性可在检索侧做 tombstone 过滤（见 [13](#13-rag-常见失败模式--本项目的应对)） |
| collection 不存在/维度不匹配 | 启动 `ensure_vector_store` 幂等创建 + 维度校验；Milvus 挂了不影响应用启动（**fail-open**） |
| 阈值判断方向（IP 度量越高越相似） | IP 下保留 `distance > threshold` 的命中；若换成 COSINE 度量需同步调整判断方向 |

## 7. BM25 关键词通道

### 7.1 实现要点（`bm25.py`）

- **分词**：英文/数字按单词，**中文按单字**切分（`[a-zA-Z0-9_]+|[\u4e00-\u9fff]`），可配 `BM25_USE_JIEBA=true` 切 jieba 词；内置约 60 个高频中文**停用词**。
- **公式**：Okapi BM25，`k1=1.5, b=0.75`，平滑 IDF `ln(1+(N-df+0.5)/(df+0.5))`（避免除零）。
- **索引缓存**（`hybrid.py`）：按 `(文档集签名, user_id)` 做 `lru_cache`；签名 = 行数 + 最新 `created_at`，TTL 5s；摄入/删除后 `invalidate_docs_signature()` 立刻失效。
- **防爆炸**：块数超过 `bm25_max_docs(5000)` 时跳过 BM25 通道。

### 7.2 为什么这样设计

- **纯向量检索覆盖不了精确关键词**：专有名词、型号（`BAAI/bge-small-zh-v1.5` 这类）、代码、编号等**字面敏感**查询，embedding 可能"语义相近但字面跑偏"，BM25 恰好补上。
- **零第三方依赖实现**：不引入 Jina/SPLADE；中文字符天然适合单字切分（2-3 字词可被单字重叠召回），够用且索引构建极快。
- **签名 + TTL 缓存**：避免每次检索都全量构建索引（`O(文档数)`），同时摄入后主动失效保证**秒级可见**——"缓存一致性"在关键词通道的落地。
- **5000 块上限**：BM25 建索引 `O(N)`、打分 `O(N)`，超过阈值时内存/CPU 不可控，直接跳过保命。

### 7.3 潜在问题与解法

| 问题 | 解法 |
|------|------|
| 单字切分在长尾术语上召回噪声大 | 开 `BM25_USE_JIEBA`（词切分），或检索前用 query 改写补充同义词 |
| 停用词表是静态写死的 | 可按领域扩词表；或仅对超长查询启用停用词过滤 |
| 5000 块以上退化为纯向量（关键词能力消失） | 保持双通道——用独立 BM25 实例（Lucene/OpenSearch）或升级分布式稀疏检索 |
| 索引重建与写入并发（摄入中检索读到旧索引） | 签名 TTL + 主动失效把窗口压到秒级；如需强一致可对"正在摄入的 source"加读锁 |

## 8. 混合检索与 RRF 融合

### 8.1 实现要点（`hybrid.py::search_hybrid`）

```
filter_expr = user_id == "<user>"          # 向量通道的 user 过滤

dense  = vector_store.search(query, top_k*3, threshold, filter_expr)  # 通道1
bm25   = BM25Index.search(query, candidate_k=20)                      # 通道2

融合键 fid = f"{doc_id}:{chunk_index}"      # 跨通道对齐的契约
ranked_lists = [dense_list]
if bm25_list: ranked_lists.append(bm25_list)

fused = RRF(ranked_lists, k=60)[:top_k]
# score(item) = Σ 1/(k + rank + 1)
```

### 8.2 为什么这样设计

- **RRF（Reciprocal Rank Fusion）是业界标配融合算法**：不依赖各通道分数可比值（向量 IP 与 BM25 分数量纲完全不同、无法直接加权），只依赖**排名**。
- **融合键 = `doc_id:chunk_index` 是混合检索里的"数据契约"**：两路检索各自排序，合并时必须知道"向量第 3 名"和 "BM25 第 2 名"是不是同一块。用复合键让跨通道对齐退化为 `O(1)` 字典查找，是正确性的根基。
- **交集加分**：语义 + 关键词都命中的块得到两路分数自然排前；纯 BM25 命中也能进入 Top-K——补齐向量"语义鸿沟"错过的精确内容。
- **`k=60` 平滑**：`1/(k+rank)` 中 `k` 越大对低排名的惩罚越小；60 是业界常见稳定值。

### 8.3 潜在问题与解法

| 问题 | 解法 |
|------|------|
| 向量候选 `top_k*3` 与 BM25 候选 20 数量不对称 | 候选数已配置化（`HYBRID_CANDIDATE_K`），用评估集调参 |
| RRF 只给命中项计分，未命中项被丢弃 | 这是特性——排序只需命中项；若要保底可叠加"高相似度兜底" |
| 将来增加更多检索源（稀疏向量/SQL 等） | `_rrf` 天然支持 N 路 ranked_lists，无额外融合代码 |
| 语义通道被 0.35 阈值滤掉过多 | 阈值应按 embedding 实测分布调整（`RAG_SCORE_THRESHOLD` 配置化），并看命中数统计 |

## 9. Rerank 精排

### 9.1 实现要点（`rerank.py`）

```
candidates = hits[:rerank_candidate_k]      # 仅精排前 6 条候选（控制 CPU 推理量）
pairs = [(query[:512], text[:512]) ...]     # 输入截断，减少 token
scores = CrossEncoder.predict(pairs)        # (query, doc) 联合编码打分
ranked = sorted(zip(candidates, scores), desc)[:rerank_top_k]
失败时 → 原样返回 hits[:top_k]（优雅降级）
```

### 9.2 为什么这样设计

- **Bi-Encoder 检索 → Cross-Encoder 精排是生产级 RAG 的标准范式**：Bi-Encoder 对 query 和 doc **独立编码**（快，可批量），但丢失交互信息；Cross-Encoder 拼接 `(query, doc)` **联合编码**，精度显著更高但慢——所以只对 Top-N 精排，**成本受控**。
- **候选受限 `rerank_candidate_k=6`**：精排延迟 ≈ 候选数 × 单次推理，限制在 6 条把 CPU 推理压住（文档注释："越小越快，质量略降"——显式的**质量/延迟权衡**）。
- **`rerank_max_length=512` 截断**：控制 token；过长的块重排时拟合噪声。
- **后台预热**（`main.py::_warmup_sync`）：rerank 模型首载约 1.1GB，启动后后台线程加载，避免**首个 RAG 请求卡顿**（冷启动优化）。
- **优雅降级**：模型加载/推理异常 → 直接返回未精排 Top-K，**检索不掉线**（fail-open 原则贯穿本项目）。

### 9.3 潜在问题与解法

| 问题 | 解法 |
|------|------|
| 候选 6 条太少导致精排"矮子里拔将军" | 增大 `rerank_candidate_k` 到 10~20（加延迟）；或换 GPU 批量推理 |
| 精排只对 query 与块文本打分，感知不到查询意图改写 | 先做 query 改写（见 [13](#13-rag-常见失败模式--本项目的应对)）再进入精排 |
| rerank 分数与 RRF/向量分数并存 | `_hit_key` 定义了排序优先级（rerank > rrf > 向量 > bm25）；转 Document 时 metadata 保留全部分数便于评估 |

## 10. 检索器与上下文压缩

### 10.1 实现要点（`retriever.py`）

```
invoke(query)
  候选数 = rerank 开 ? min(top_k*3, rerank_candidate_k) : top_k
  检索   = hybrid.search_hybrid 或 vector_store.search（按 HYBRID_SEARCH 开关）
  精排   = rerank(...) or hits[:top_k]
  → _dedupe_and_merge(hits, rag_max_per_doc)   # 上下文压缩第一层
  → 块长 > rag_max_chunk_chars 截断              # 上下文压缩第二层
  → 转 LangChain Document（metadata 全量透传）
```

### 10.2 `_dedupe_and_merge`——上下文压缩的关键

同一 `source` 的命中按分降序排序，核心逻辑:

1. **同文档限流**：每个 source 最多保留 `rag_max_per_doc(2)` 条 → **防止 Top-K 被同一章节占满**，把名额释放给更多文档（提升覆盖率 / recall）。
2. **同 (source, chunk_index) 去重**：清掉 Milvus 残留的重复向量（双写/删除的副作用）。
3. **相邻块合并**：`chunk_index` 连续（如 3 → 4）的块**文本拼接** → 保持章节上下文完整（如标题块 + 正文块合成一条）。合并后**全局重排**。

### 10.3 为什么这样设计

- **上下文预算意识**：LLM 上下文有限 + **"lost in the middle"**（长上下文中位置靠中间的内容注意力下降）。与其喂 10 条碎片，不如喂 4-6 条"完整语义单元"——**每 token 的信息密度最大化**，比单纯调大 top_k 更有效。
- **两级压缩协同**：`去重合并`（结构层面）+ `长度截断`（字符层面），后者防止单个超长块挤爆令牌预算，也让 rerank/生成阶段更聚焦。
- **元数据全量透传**：`source/chunk_index/score/vector_id/rrf_score/rerank_score` 等 → 前端**引用溯源**与检索质量排查共用（同一套数据既服务用户又服务调试）。

### 10.4 潜在问题与解法

| 问题 | 解法 |
|------|------|
| 相邻合并后文本超长 | 合并后再按 `rag_max_chunk_chars` 截断（代码顺序已保证） |
| 想按"语义段落"合并而非"序号连续" | 可改为基于 metadata 的段落边界合并；当前序号连续已覆盖多数"标题-正文"场景 |
| 合并会把多源内容混入一条 | 按 source 分组处理，不会跨文档合并——分组内合并天然隔离文档边界 |

## 11. RAG Agent 集成与用户隔离

### 11.1 `_build_search_knowledge_base_tool`（`tools.py`）

```python
rt = get_runtime()                     # LangGraph 运行时上下文
user = rt.context.user_id or "default" # 取出当前对话用户
retriever = get_retriever(user_id=user) # ★ 全链路按用户隔离
docs = await asyncio.to_thread(retriever.invoke, query)  # 不阻塞事件循环
# 输出: "[1] 来源: xxx.md\n<text>"  → 给 LLM 的格式化上下文
_record_rag_sources(user, sources)     # 记录引用来源，供前端溯源
```

### 11.2 用户隔离的四层防线

| 层 | 隔离手段 |
|----|---------|
| 向量 | Milvus `filter=user_id=="<user>"` + user_id Trie 索引 |
| 关键词 | BM25 索引按 (签名, user_id) 缓存，SQL `WHERE user_id == ...` |
| 元数据/文件 | Postgres `Document.user_id`；上传按用户校验归属；下载 `_safe_source_in_uploads` 防任意文件读取 |
| 生成链路 | 工具经 `get_runtime().context.user_id` 取用户，每轮按该用户构建 retriever（见 11.1） |

**为什么在工具内取用户而不是全局拿**：Agent 是并发执行的（多会话共享图实例），用户身份必须通过运行时 context 传入，才能避免 **A 用户会话检索到 B 用户知识库**的越权——这是多租户 RAG 最容易踩的安全坑。

### 11.3 引用溯源设计

- 检索工具执行后把命中 `source` 写入 `_RAG_SOURCES[user_id]`（进程内单槽），supervisor 发 `tool` 事件时读出附到 `data.sources`，前端气泡展示来源文件名。
- **为什么用"最近一次"单槽**：一个会话轮内的 RAG 命中来源以"最后一次检索"为准（supervisor 一般调一次）；持久化靠 `Message.sources` JSON 字段（跨会话回溯）。

### 11.4 潜在问题与解法

| 问题 | 解法 |
|------|------|
| 进程内 `_RAG_SOURCES` 重启即失 | 对话结束即写 `Message.sources` 持久化；内存态只负责"流式推送瞬间" |
| 多租户共享图缓存（`build_rag_agent` 是 lru_cache） | 图/工具共用，但每轮 `user_id` 来自运行时上下文 → 天然按调用隔离 |
| 检索文本直接喂 LLM → prompt 注入风险 | ✅ 已实现：外部内容按「不可信数据块」隔离（`wrap_as_data`）+ 注入指令检测剔除 + 用户 query 拒绝（`app/rag/prompt_injection.py`） |

## 12. API 设计与后台任务（`rag.py`）

### 12.1 上传即响应、后台摄入、前端轮询

```
POST /api/rag/upload
  → 校验扩展名(415)、大小(413)、路径穿越(只取文件名)
  → 原始文件持久化到 uploads/<uuid>/
  → 注册 task_id → threading.Thread(_run_ingest) 立即返回 {"tasks": [...]}
GET /api/rag/ingest/{task_id}   # 前端轮询：pending/processing/done/error + 阶段%
```

### 12.2 为什么这样设计

- **上传接口不阻塞**：embedding + Milvus 写入可能是秒级~分钟级，同步返回会让 HTTP 长挂。拆成"注册任务 + 轮询进度"是**长耗时写入的标准模式**（类比 GitHub Actions 的 run_id）。
- **原始文件持久化**：不存临时目录，`uploads/<uuid>/` 持久保留 → 支撑在线预览/下载/审计/重索引（企业合规要求）。删除文档时 `rmtree` 整个 `<uuid>/` 目录。
- **进程内任务表**：`_INGEST_TASKS` 带锁 + 上限 20 条保护，超限丢弃最旧完成态任务（内存安全）。
- **进度分段**：5% 读文件 → 15% 分块 → 35% 清理 → 40% 嵌入 → 80% 写库 → 100%，用户可见"在哪一步"，避免摄入成为黑盒。

### 12.3 潜在问题与解法

| 问题 | 解法 |
|------|------|
| 进程重启任务丢失 | 前端轮询 404 = 任务不存在，可提示重传；如需持久可存入 DB（已存在 tasks 表可扩展） |
| 大并发上传排队轰炸 embedding | 加信号量/线程池上限；当前单机场景可接受 |
| 删除 source 时只删 uploads 内原始文件（库外 source 保留） | 按 `_safe_source_in_uploads` 判断，避免误删第三方目录 |
| 上传与检索并发（读后写见 4.3） | 检索端签名 TTL 秒级收敛；需会话级一致可对单文档摄入加读锁 |

## 13. RAG 常见失败模式 & 本项目的应对

> 综合《Seven Failure Points When Engineering an RAG System》（Barnett 等）、
> RAGAS 评估框架、业界博客（读后写竞争 / 检索级联失效）以及本项目的实测经验。

### 13.1 失败模式总表

| # | 失败模式 | 症状 | 常见根因 | 本项目现状 / 对策 |
|---|---------|------|---------|------------------|
| 1 | **内容缺失（Missing Content）** | 知识库没答案，仍给"看似合理"的回答 | 知识库覆盖不足；LLM 不懂承认不知道 | RAG prompt 明令"检索不足时明确告知库中没有，禁止编造"；数据质量优先 |
| 2 | **错过关键文档（Missed Key Doc）** | 答案在库内但排名太低没被返回 | chunk/top_k 不当；embedding 不适配；无 rerank | 标题+中文分隔符分块 + 混合检索 + rerank + 候选 `top_k*3` 放大召回 |
| 3 | **上下文冲突 / 整合失败（Context Conflict）** | 正确文档被召回但未进入生成上下文 | top_k 过大被噪声淹没；去重/合并弱 | `_dedupe_and_merge`：同文档限流 + 相邻合并，控制信息密度 |
| 4 | **语义鸿沟（Semantic Gap）** | 用户口语问题 vs 文档书面语 | Bi-Encoder 独立编码；短查询 × 长文档 | 混合检索 BM25 补"字面命中"；可扩展 Query 改写 / HyDE（见 13.3） |
| 5 | **幻觉（Hallucination）** | 编造引用、错误事实 | 上下文不足/被忽略；prompt 不约束 | 检索结果格式化为 `[i] 来源: xxx` + prompt 约束，前端展示引用溯源 |
| 6 | **lost in the middle** | 多块上下文中的中间块被 LLM 无视 | 上下文过长 | 上下文压缩控制块数（见 [10](#10-检索器与上下文压缩)）；后续可做相关块前置 |
| 7 | **读后写竞争（Read-after-write race）** | 引用已删除/已修改的文档 | 检索与生成间的快照不一致；索引延迟删除 | 摄入原子性 + 秒级签名失效；强一致见 13.2 |
| 8 | **检索级联失效（Ghost embedding）** | 删除文档后仍被检索命中 | 向量与源不一致；无稳定 ID/删除映射 | 稳定 ID + Postgres sidecar + `delete_by_ids` 双删 + 签名失效（见 [4]） |
| 9 | **数据质量虫（脏 chunk / 解析丢内容）** | 召回的片段残破、乱码 | OCR 缺失、编码错误、表格丢数据 | 多格式解析 + 编码检测 + 表格并入（见 [2]） |
| 10 | **权限 / 隔离泄露** | 用户检索到他人文档 | 过滤被忽略；全局索引 | `user_id` 四层防线（见 [11]） |

### 13.2 读后写竞争 / 索引一致性的工程解法（若需更强一致）

本项目当前处于"秒级最终一致"级别：`ingest` 原子 + 主动失效把窗口压到秒内。若面向合规/医疗/金融等强一致场景，业界通用解法：

1. **为分块加版本/新鲜度**：每个 chunk 存 `last_verified_at`，检索时过滤 `last_verified_at < now - TTL` 的块——**平滑降级**而非"幽灵引用"。
2. **引用前重新校验**：生成前按 doc_id 回查存在性 + 内容 hash 是否仍匹配，不匹配则丢弃引用重新生成（多一次往返，换 read-your-writes 语义）。
3. **事务性检索（乐观并发）**：处理期间源文档变更则整个请求失败，适合"绝不允许基于过期数据回答"的场景。
4. **CDC（变更数据捕获）**：从"上传触发索引"升级为订阅日志流实时刷新向量（Milvus-CDC / pgvector 逻辑解码），把嵌入延迟压到亚秒级——竞争窗口缩小，工程复杂度上升。

### 13.3 检索优化三板斧（评估后可扩展）

| 招数 | 说明 | 本项目现状 / 接入点 |
|------|------|---------------------|
| **Query 改写** | 口语 query → 同义改写 / 多路改写取并集 / 拆子问题 | ✅ 已实现：`rule`（去口语框架词+同义并列，零依赖、CI 可挂）/ `llm`（改写为精炼检索词，失败/拒绝模板回退）；默认关闭，实验结论与 A/B 复现见 [EVALUATION_REPORT](EVALUATION_REPORT.md) |
| **HyDE** | LLM 先写"假想答案"再向量化检索，弥合 query-doc 差距 | 未实现；适用领域文档；注意首 token 延迟、事实型查询慎用 |
| **混合双路 + 精排** | BM25 + Dense + RRF + Cross-Encoder | ✅ 已实现（见 8 / 9） |

### 13.4 排查方法论（先度量再动手）

调 RAG 最忌凭感觉改参数。流程：真实问题集 → 跑 RAGAS → 看四指标定位图层（见 [15](#15-评估方法论)）→ 每次只动一个变量，A/B 对比。

## 14. 设计难点总结

按权重从大到小：

1. **两库一致性（Milvus + Postgres）是最大难点**：写入顺序、失败回滚、删除的扇出（1 文档 → N 块）、缓存失效（BM25 签名）…… 每项对不齐都会出现"半个库"。本项目方案 = **Postgres 唯一事实源、Milvus 派生缓存、`doc_id` 串起映射、同一事务边界后统一双写**。
2. **融合两路不同量纲的分数**：向量 IP 分数与 BM25 分数不可比 → RRF 把"分数问题"转成"排名问题"；再叠加 rerank 第三种分数，`_hit_key` 定义优先级。
3. **上下文窗口管理与信息密度**：LLM 上下文有限 + lost-in-the-middle → 去重 + 合并 + 限流 + 截断四层压缩，宁可少而精。
4. **中文语料特殊性**：编码检测、单字/词切分、句号级分隔符、停用词——中文每一步都和英文不同。
5. **多租户安全**：隔离须贯穿"存储字段 → 检索过滤 → 文件路径校验 → 展示溯源"四层，任何一层漏都是越权。
6. **冷启动体验**：1.1GB rerank 模型 + embedding + 首次 BM25 建索引，不预热会让第一个用户苦等 → 启动后台线程预热 + 请求侧按需构建兜底。
7. **"够用就好"与过度设计**：刻意未上语义分块 / CDC / HNSW 等重型方案，用"结构化递归分块 + sidecar 映射 + 秒级签名失效"满足当前中小规模知识库——**刻意的架构决定而非能力缺失**。

## 15. 评估方法论

### 15.1 评估闭环（推荐）

| 环节 | 动作 |
|------|------|
| **真实问题集** | 从会话日志采集 100+ 条真实 query（标注期望答案与相关文档 source） |
| **指标（RAGAS 体系）** | `Context Precision`（检索精度）/ `Context Recall`（召回）/ `Faithfulness`（忠实）/ `Answer Relevancy`（切题） |
| **分环节定位** | 指标低 → 定位图层（见下表映射） |
| **A/B 参数对比** | 同一 eval 集上对比 chunk_size / top_k / 是否混合 / rerank 候选，用数据说话 |
| **动态用例** | 增加"检索后修改语料"的用例，捕获读后写竞争（见 13.2） |

四个指标的含义与排查映射：

| 指标 | 测什么 | 偏低 → 查哪层 |
|------|--------|--------------|
| Context Precision | 召回内容中真正相关的占比 | 检索精度：rerank 候选 / 阈值 / embedding |
| Context Recall | 该召回的召回了多少 | 召回：chunk 切分 / 语料覆盖 / top_k |
| Faithfulness | 答案是否忠于上下文 | 生成：prompt 约束 / LLM 能力 / 上下文压缩过头 |
| Answer Relevancy | 答案是否切题 | 生成：Query 改写 / prompt 模板 |

### 15.2 本项目已有的评估与测试

- **纯逻辑单测**：`test_rrf.py` / `test_bm25.py` / `test_chunking.py` / `test_sql_validation.py`。
- **集成测试**：`tests/test_api.py` 覆盖 RAG 上传 / 检索 / 删除（DB 不可达自动跳过）。
- **检索评估脚本**：`scripts/eval_rag.py` 固定问题集 top-k 命中率。

**差距**：尚无 RAGAS 四指标端到端自动化闭环——是后续提升质量性价比最高的投资方向。

## 16. 面试 Q&A

> 视角：**AI 应用开发 / RAG 方向技术面试官**。每题附"考察点 + 回答要点"。

### Q1. 为什么"向量库 + 向量检索"是最优解？直接关键词搜不行吗？

**考察点**：理解向量检索与关键词检索的互补性。

**要点**：(1) 向量把语义映射到向量空间，能抓"语义相同、字面不同"；(2) 但纯向量丢专名/型号/代码等字面精确命中。生产环境几乎都是 **Hybrid（关键词 + 向量）+ 精排**；本项目即 BM25 + Milvus + RRF + Cross-Encoder。

### Q2. 分块怎么选？块太大/太小各有什么问题？

**考察点**：参数敏感性与文档类型差异化。

**要点**：过大 → 噪声淹没、token 浪费、难以命中局部信息；过小 → 语义断裂、上下文不足。本项目用 `RecursiveCharacterTextSplitter` + 中文句号分隔 + 10~20% 重叠，Markdown 加标题层级切分保证块自包含。**分块策略应随文档类型分化**，并用 eval 集调参。

### Q3. 增量摄入怎么实现？摄入时用户正在检索怎么办？

**考察点**：增量成本意识与一致性。

**要点**：(1) 内容 sha256 指纹 → 相同块不重嵌入、消失块双删；(2) Postgres 权威 + 双写；(3) 摄入中检索靠签名 TTL + 主动失效实现秒级最终一致；强一致加块版本号（见 13.2）。

### Q4. rerank 为什么放最后？为什么不用向量分数直接排序？

**考察点**：Bi-Encoder vs Cross-Encoder 的本质差异。

**要点**：Bi-Encoder 独立编码、快但丢交互；Cross-Encoder **拼接联合编码**、精度高但慢。因此生产管线"宽召回 → 少精排"；精排成本 = 候选数 × 单次推理，候选必须限流（本项目 `rerank_candidate_k=6`）。

### Q5. RRF 比加权求和好在哪里？

**考察点**：多源分数的"不可比"问题。

**要点**：(1) BM25 分与向量 IP 分数量纲/分布完全不同，无法直接加权相加；(2) RRF 只看**名次**不看分数，`1/(k+rank)` 无损融合各路的排序信息；(3) 交集项天然加分，实现简单、业界验证有效。

### Q6. 多租户 RAG 怎么按用户隔离？如何防止越权？

**考察点**：多租户安全。

**要点**：贯穿四层——数据模型（`user_id` 字段 + 向量过滤表达式）、检索（BM25 按用户缓存/过滤）、资源访问（预览/下载前归属校验 + `_safe_source_in_uploads` 防任意文件读取）、生成链路（`get_runtime().context.user_id` 每轮传入）。测试：写"用户 A 检索用户 B 文档"的负向用例。

### Q7. 上下文是不是越长越好？做了哪些压缩？

**考察点**：对 LLM 注意力与成本的认知。

**要点**：不是越长越好——噪声多、token 贵、中间内容注意力下降（lost in the middle）。本项目压缩链：rerank 候选裁剪 → 同文档限流（2 条/文档）→ 相邻块合并 → 单块 1500 字符截断，最终喂给 LLM 的是"少而完整的语义单元"。

### Q8. 检索质量差，你怎么排查？

**考察点**：真实调优经验，而非背 Demo。

**要点**：先量化定位：跑 RAGAS，按 15.1 的指标映射表找到图层，再对症下药（Recall 低 → 分块/语料；Precision 低 → rerank/阈值；Faithfulness 低 → prompt/LLM）。**每次只动一个变量，做 A/B**，绝不凭感觉连改多个参数。

### Q9. 换 embedding 模型要注意什么？

**考察点**：模型版本治理。

**要点**：(1) 维度变化要重建集合 + 全量重嵌（项目已有维度校验防静默错配）；(2) 换模型后旧向量与新向量**空间不可比**——新旧混存=垃圾进垃圾出；(3) 需要和 rerank 模型一起重评，避免检索/精排失配。

### Q10. 长文档（100+ 页）怎么办？

**考察点**：分层检索能力。

**要点**：(1) 分层索引：章节摘要中心 → 章节分块 → 叶子块检索，多跳 MRR；(2) 本项目当前单层（标题 + 块），超长文档可升级"章节索引 + 块检索"两级；(3) `RAG_MAX_PER_DOC=2` 已天然防"一章霸榜"。

### Q11. 如果检索结果混入过时/错误信息，你能做哪几层防御？

**考察点**：纵深防御意识。

**要点**：数据层（增量抖动、新鲜度校验、CDC）；检索层（过滤 + 阈值）；生成层（prompt 约束 + 要求给出来源）；展示层（引用溯源可点开原文）；评估层（负向用例捕获过时引用）。单点失效不至于全盘皆错。

### Q12. `doc_id:chunk_index` 为什么偏偏用作融合键？

**考察点**：对全局对齐的"数据契约"意识。

**要点**：两路检索（向量/BM25）各自排序，合并时必须知道"向量第 3 名"和"BM25 第 2 名"是不是同一块。复合键让跨通道对齐退化为 `O(1)` 字典查找，是混合检索正确性的根基。

### Q13. 你自己动手实现了哪些 RAG？踩过最大的坑是什么？

**考察点**：区分"用过"与"做过"。

**要点**（结合本项目）：最大的坑是**两库一致性**——Milvus 与 Postgres 的映射、删除扇出、BM25 缓存失效；用"Postgres 唯一事实源 + doc_id sidecar + 主动失效 + 原子顺序"化解。第二坑是**中文分块**——英文分隔符直接套中文会切碎语义，改为句号级分隔 + 重叠后召回明显改善。
